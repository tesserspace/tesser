# 01. 用户画像与 JTBD（Personas & Jobs-to-be-done）

> 目标：先把“谁在用、为什么用、用完算成功/失败”定义清楚，避免 PRD 变成堆功能。

## 0) Persona 优先级（用于取舍）

> PRD 写作与排期时默认按该优先级取舍；若与实际不符，需要在 `03-decisions-open-questions.md` 里调整。

- P0：策略研究者（Researcher）
- P1：交易系统工程师（Trading Systems Engineer）
- P2：微观结构/盘口研究者（Microstructure / LOB Researcher）
- P3：回测评审者/管理者（Reviewer / PM / Lead）
- P4：数据工程/数据管理员（Data Engineer / Dataset Curator）

## 1) Persona A：策略研究者（Researcher）

### 背景
- 关注点：策略想法验证、参数调优、回测对比、快速复盘。
- 数据形态：以 candles 为主（分钟/小时/日），偶尔需要 tick/盘口做验证。

### JTBD（要完成的事）
- 我想快速把一个策略配置跑起来，并在 1 分钟内知道“是否值得继续研究”。
- 我想对比多个 runs（不同参数/不同数据区间/不同费率假设），快速定位性能差异来源。

### 成功标准（用户视角）
- 能在 GUI 中完成：选数据 → 选策略 → 填参数 → 运行 → 看曲线/指标 → 生成对比结论。
- 对比时能复用同一视图（同一指标表、同一图表叠加规则），并能导出报告/图片/数据。
- 能管理自己的“实验库”：搜索/标注 runs（例如：策略版本、参数组、结论标签），避免结果丢失在文件夹里。

### 常见失败模式
- 不清楚回测语义（lookahead、成交价、手续费、滑点）导致“结果看起来很好但不可用”。
- 图表卡顿/加载慢导致无法交互式探索（尤其是长时间窗或多 runs 对比）。
- run 结果无法复现（换机器/换版本就对不上）。

### 必需能力（Must-have）
- Run Launcher：策略与参数编辑（至少 TOML），可保存为 preset。
- Run Detail：指标 + equity/drawdown + 交易列表（分页）+ 导出 artifacts。
- Runs Compare：多 run 叠加与表格对比；快速筛选（按策略/时间/数据集）。
- 语义显式化：默认 no-lookahead；执行模型参数必须可见且写入 metadata。

## 2) Persona B：交易系统工程师（Trading Systems Engineer）

### 背景
- 关注点：语义严谨、组件可复用、结果可审计、对齐生产系统。
- 数据形态：更可能使用 tick/LOB（或 flight recorder）验证执行与撮合假设。

### JTBD
- 我想验证回测引擎（Full）在不同执行模型/延迟/队列假设下的表现差异，并定位原因。
- 我想把一次 run 的全部 inputs/outputs 固化，作为回归测试/版本升级的对照基线。

### 成功标准
- 每次 run 都有完整的 RunSpec + 数据 fingerprint + 版本信息，可计算重放。
- 能查看更细粒度的事件链路：signals → orders → fills → portfolio 更新（哪怕先是摘要）。

### 失败模式
- 结果缺少可追溯链路：只剩指标，没有“为什么会这样”的证据。
- tick/LOB 回放导致资源耗尽（内存爆/磁盘爆）且 UI 没有预估与降级路径。

### 必需能力
- Full 引擎的语义面板：撮合/队列/延迟/费用模型的配置与解释。
- artifacts 分层：默认摘要，用户显式选择才保存全量事件。
- Job 模型：长任务进度、取消、重试、日志与错误码。

## 3) Persona C：微观结构/盘口研究者（Microstructure / LOB Researcher）

### 背景
- 关注点：盘口形态、冲击成本、滑点、成交与盘口演化的关系。
- 数据形态：tick + L2/L3（LOB）密度极高，窗口跨度可从秒到周。

### JTBD
- 我想在一个时间窗里回放盘口，叠加自己的订单/成交轨迹，理解执行质量。
- 我想生成 heatmap/统计（时间×价位流动性、成交密度、价差分布），并能快速缩放到异常段。

### 成功标准
- 能在“大窗口粗粒度”下快速定位异常段，再 zoom-in 到秒级/事件级细节。
- 可视化不要求全量事件进前端：后端提供 tiles/聚合与按需查询。

### 失败模式
- UI 直接加载全量 tick/LOB 导致不可用（渲染/GC/内存爆）。
- 没有多分辨率缓存，任何 zoom 都要重新扫描全量数据。

### 必需能力（阶段性实现）
- LOD/Tiles 的架构（先在 PRD 定义，后续逐步实现 tick/LOB 专用 tiles）。
- 查询 API 以“时间窗 + 目标分辨率”为核心参数。

## 4) Persona D：回测评审者/管理者（Reviewer / PM / Lead）

### 背景
- 关注点：结果可信度、对比结论、可复现证据、风险提示。

### JTBD
- 我想快速查看某策略版本在多个数据区间/假设下是否稳定，并做 go/no-go 决策。
- 我想看到 run 的关键假设是否合理（手续费、滑点、是否允许做空等）。

### 成功标准
- 对比视图清晰：指标对齐、曲线对齐、相同基准与货币单位。
- 每个结论都有可追溯 artifacts（数据、参数、版本）。

### 失败模式
- 指标定义不一致/四舍五入不一致，导致“看似差异”其实是定义问题。
- UI 无法解释差异来源（不同引擎/不同执行模型/不同数据 fingerprint）。

### 必需能力
- 标准化指标定义与展示（在后续 PRD 固化字段、单位、计算方式）。
- RunSpec/metadata 可视化：用一屏解释“这次 run 到底怎么跑的”。

## 5) Persona E：数据工程/数据管理员（Data Engineer / Dataset Curator）

### 背景
- 关注点：数据下载/归一化/校验/重试、磁盘与缓存占用、数据版本管理。
- 数据形态：大文件、多分区 Parquet；长期需要 tick/LOB（更大）。

### JTBD
- 我想从交易所下载数据并实时看到进度、速率、失败原因；失败可以续传/重试。
- 我想把原始数据标准化为 Tesser 的 canonical 格式，并能快速校验缺口与异常。
- 我想控制本机缓存与 artifacts 的空间占用（清理策略、保留策略、按项目隔离）。

### 成功标准
- 数据任务可观测：进度条 + 日志 + 失败可定位（HTTP/限流/解析/schema 不匹配等）。
- 数据集有索引与预览：不需要每次打开都扫描全量 parquet 才知道范围与质量。

### 失败模式
- 下载任务不可取消/失败不可恢复导致“重来一次”。
- 缓存与 artifacts 无上限增长，最终拖垮机器。

### 必需能力
- Dataset Index/Cache 管理页：空间占用、最近使用、清理建议与一键清理。
- 明确的数据 fingerprint 与 schema 版本；必要时提供迁移策略提示。

## 6) 横向需求汇总（按主题归类）

### 5.1 可视化性能（所有角色共性）
- 永远只渲染屏幕需要的点数（target_points + 后端下采样）
- 多分辨率 LOD/tiles（尤其是长窗口与 tick/LOB）
- 前端虚拟列表、Canvas/WebGL 渲染

### 5.2 可复现与可审计（Researcher/Engineer/Reviewer）
- RunSpec + fingerprint + 版本信息必备
- artifacts 分层（摘要/全量）
- 对比时强制显示“语义差异”

### 5.3 数据闭环（Researcher）
- 下载进度、失败重试、校验与缺口提示
- 数据集预览与索引（避免每次扫描全量 parquet）

## 7) 需要在竞品对比中验证的假设
- 哪些竞品把“可复现/审计”当一等公民？它们的 artifacts 结构与 UI 呈现是什么？
- 哪些竞品在大数据可视化上用 LOD/tiles/二进制传输？有什么可借鉴的默认阈值/预算？
- 哪些竞品能同时覆盖 candle 与 tick/LOB？它们如何处理资源消耗与降级？
